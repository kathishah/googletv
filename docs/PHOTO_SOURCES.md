# Photo source feasibility

Checked against official provider documentation on 2026-10-04. Recheck before implementing OAuth or caching because provider behavior and policies change.

## Google Photos

Google sign-in authenticates the user; the OAuth token's scopes and the Photos API determine which media the app can read. Google removed the broad `photoslibrary.readonly` access model in 2025. The Library API now focuses on media created by the app. The [Google Photos API update](https://developers.google.com/photos/support/updates) and [authorization guide](https://developers.google.com/photos/overview/authorization) explain the distinction.

The [Picker API](https://developers.google.com/photos/picker/guides/get-started-picker) lets the user explicitly choose photos. Users can search for an album title in the picker, but albums are not directly presented as an automatically syncing source in its [picking experience](https://developers.google.com/photos/picker/guides/picking-experience). Picker sessions and selected media access expire; [base URLs normally last up to 60 minutes](https://developers.google.com/photos/library/guides/access-media-items). We need to validate the policy and UX for any longer-lived slideshow before implementing it.

The [Photos Ambient API](https://developers.google.com/photos/ambient/guides/about) is designed for ambient slideshows on TVs and photo frames. It uses [OAuth for TVs and limited-input devices](https://developers.google.com/photos/ambient/guides/configure-your-app), and users configure media sources such as albums in Google Photos. However, [Google requires acceptance into the Photos partner program](https://developers.google.com/photos/partner-program/overview) before an app can access this API. A normal Google sign-in or an OAuth token from another scope does not bypass that requirement.

Google TV's [built-in Ambient mode](https://support.google.com/googletv/answer/10070821?hl=en) already offers Google Photos album selection and slideshow speed on supported devices. This is a useful baseline for testing the TV and might cover the Google-only use case without custom code.

## Apple Photos

Apple's [PhotoKit](https://developer.apple.com/documentation/PhotoKit) exposes a user's Photos library, including iCloud-backed content, to authorized apps on Apple devices. Apple's [CloudKit](https://developer.apple.com/documentation/cloudkit) concerns an app's own containers; it is not a direct API to a user's personal iCloud Photos library. We have not found a documented Apple Photos API that an Android TV app can use to sign in and browse all personal albums directly.

An optional browser experiment is [Photos on iCloud.com](https://support.apple.com/en-gb/guide/icloud/mm73262d11fe/icloud). It supports browsing albums and a [full-screen slideshow](https://support.apple.com/en-gb/guide/icloud/mmc8ef9b8a9a/icloud). In that slideshow, selected videos appear as thumbnails rather than playing as videos. Apple's [recommended iCloud.com browsers](https://support.apple.com/en-gb/118308) are desktop browsers on Mac and PC, so login, layout, and remote navigation on a Google TV browser are unverified. The website does not give our app an API for custom timing or automatic system-screensaver activation.

Chosen path for the first personal build: the TV reads available image files from the existing Mac mini SMB share. A public [iCloud Shared Album website](https://support.apple.com/en-gb/guide/iphone/ipha8f8fc3c5/26/ios/26) can be viewed by anyone with the link, but is not a private-library API and should not be treated as one.

SMB gives file access, not a Photos API. It can display locally available originals, but cannot reliably reveal album membership, edits, or iCloud-only assets. A read-only inspection of the cloned Photos database found album-to-file references for regular albums; the shared-album sample needs more work (see [album database probe](#album-database-probe-2026-10-16)). Direct Apple ID sign-in on Android TV still does not provide a documented Photos-library API. [PhotoKit access](https://developer.apple.com/documentation/PhotoKit) · [Photo library authorization](https://developer.apple.com/documentation/photokit/fetching-assets)

### Mac mini library finding (2026-10-11)

The existing SMB `Photos` share contains `Photos Library.photoslibrary`. Read-only inspection from this Mac confirmed that the package has `originals` subdirectories with readable JPEG and HEIC image data. The package also contains databases and other private implementation files. These internal directories are **not** the albums shown in Photos. Apple [warns against manually accessing or altering library contents](https://support.apple.com/en-gb/guide/photos/pht12e7a8015/mac). Keep all access read-only and treat the package schema as private and changeable; the app should tolerate layout changes and missing files rather than assuming it is a stable public API.

### Album database probe (2026-10-16)

To check whether album membership can be associated with files already on the clone, the Photos SQLite database was opened read-only with SQLite's immutable mode. The regular-album relationship is represented by `ZGENERICALBUM` (entity 34) joined through `Z_34ASSETS` to `ZASSET`. In this clone, the tables contained 764 album records; 756 had asset links, comprising 38,431 membership links and 17,474 distinct assets. Every joined asset row had a non-null directory and filename. Two sampled references resolved to readable files under `Photos Library.photoslibrary/originals`. This is evidence that regular album membership can be mapped to the cloned originals for at least the tested samples; it does not establish that every reference is current or usable, or that Apple's private schema will remain stable. No photo filenames are recorded here.

### Phase 1 regular-album cache

The user-selected flow is for the TV to read the cloned `database/Photos.sqlite` over the existing read-only SMB share on first **Choose albums** use or explicit refresh. The app must stage a local database snapshot and query the local file read-only; it should not ask SQLite to operate directly on a live SMB file. If required, matching WAL data must come from the same clone snapshot. After query and path validation, the TV atomically writes a metadata-only JSON album catalog to persistent app-private storage. Later picker and slideshow use reads that local cache. Cache loss or corruption triggers a rebuild; a failed refresh preserves the old valid cache and saved IDs. There is no Mac-generated JSON sidecar in the new plan.

The existing `tools/generate_photos_album_index.py` is research/validation tooling, not the runtime architecture. It confirmed the observed query over a local read-only clone: regular albums are `ZGENERICALBUM` entity 34 with `ZKIND=2`, joined through `Z_34ASSETS` to `ZASSET`; `ZUUID` is used as an opaque album ID. The Android implementation runs this query against a staged local read-only SQLite database and writes a versioned app-private JSON cache. It rejects unsupported extensions and unsafe relative paths, and playback checks SMB readability when resolving selected paths. The cached catalog and persistent cover thumbnails have been displayed on the TCL. TV-side database refresh and query timings still need repeatable validation; copying the database and WAL sequentially does not prove a coherent snapshot if the library changes during transfer.

Broader spot validation on 2026-10-17 checked one asset reference from each of 24 distinct regular albums: 22 were existing, readable supported image files under `originals`; two were excluded as unsupported or video; none were missing/unreadable or out of root. A full generator pass then checked the clone: 758 regular album candidates, 756 with links, 38,431 membership links, and 17,474 distinct database assets; all 758 candidates had distinct, non-null `ZUUID` values. Of membership rows after within-album duplicate collapse, 33,302 mapped to readable supported files under `originals`, 4,010 were unsupported or video, 3 were missing, 1,116 pointed outside `originals`, and 0 were unreadable. There were no duplicate paths within an album. The index contains 33,302 album-path references to 15,091 unique usable paths; 11,041 paths are shared by multiple regular albums and the TV deduplicates them. These results apply to this clone only; UUID continuity across an actual CCC refresh was not observed.

Twenty-five HEIC files in the clone were all 0600, and so were the same 25 files in the live library. Of 25 JPEGs, 17 were 0600 and 8 were 0644 on both drives. The user's umask is 0022. Ten sampled 0600 HEICs had no ACLs. Why Photos writes some originals as 0600 and others as 0644 is still unknown. The xattrs are suggestive of iCloud Photo Library involvement, but the 0644 files' xattrs have not been compared. Whether SMB Guest could read 0600 files if the clone volume ignored ownership is untested. Changing CCC's permission handling or the clone volume's ownership setting, adding a post-clone permission step, or using an export folder are product decisions for the user. A user-run trial made 25 HEICs 0644 in the live library with `chmod go+r`. Photos still displayed them, and the mode survived a Photos session. ### What originals contains

`originals` holds every original the library has downloaded, not just what the Photos app shows in its main view. Expected behavior based on how Photos stores files, not yet verified against this library:

- **Hidden photos** are flagged in the database only; their files stay in `originals`.
- **Recently Deleted** items keep their files until they are permanently deleted (after about 30 days or when emptied).
- **Edits are not applied.** Crops, rotations, and adjustments made in Photos live elsewhere in the package; `originals` holds unedited files.
- Screenshots, document scans, receipts, and Live Photo `.mov` companion files are mixed in with ordinary photos.

An "all of originals" slideshow on a shared living-room TV can therefore show hidden and recently deleted photos. The user chose `originals` as the default for this personal app and does not want a separate warning or opt-in. A separate export folder could provide hidden/deleted filtering, applied edits, or files that exist only in iCloud, but exported photo copies are not part of the current album-selection plan. The TV reads available originals over the same SMB share.

### SMB authentication test (2026-10-11)

The Mac mini's `Photos` share is configured for SMB Guest access and read-only access. From the development Mac, an explicit Guest mount (`//guest:@<host>/Photos`) could read the library's `originals` directory and three sample images; the recursive inventory completed. The share listing probe also accepted Guest access. Current-session authentication and anonymous-only access were rejected. This establishes that the server accepts SMB Guest access, not anonymous access; an Android SMB client must offer an explicit Guest mode (or equivalent guest credentials). Do not treat an arbitrary username with a blank password as Guest. This was tested from the development Mac, not the TV, and does not establish that the app's SMB client works on the TV. SMB1 is obsolete and insecure, and macOS file sharing is built around SMB2/3, so the Android client library must support SMB2 or later.

Because the share is readable by Guest, any device on a network that can reach the Mac mini's SMB service may be able to read its contents. Keep the share read-only and limit network reachability to the intended local network.

### Android TV client check (2026-10-12)

The read-only Android adapter uses SMBJ 0.15.0 with its explicit Guest authentication mode. Initial TV tests failed during SMB session setup with `SMB2GuestSigningRequiredException`; they did not reach share listing or image reads. SMBJ refuses a Guest session when the server advertises message signing as required. This matches [SMBJ issue 554](https://github.com/hierynomus/smbj/issues/554), which reports the same Guest/signing incompatibility with a macOS file server. The 0.15.0 source retains this check. Enabling SMBJ's multi-protocol negotiate option alone did not change the TV result. The issue tracker suggests combining that option with `withSigningRequired(false)`; testing that exact combination on the TV still failed with the same exception. Restricting the Android client to SMB 2.0.2/2.1 dialects also failed with the same exception, so that restriction was removed. A separate development-Mac probe with jcifs-ng 2.1.9 also failed authentication, so it is not a validated replacement.

Apple's [SMB troubleshooting note for Macs bound to Open Directory](https://support.apple.com/en-ae/101956) says macOS uses SMB3 by default and documents configuring the SMB server to accept SMB2 only by setting `ProtocolVersionMap` to `2`. The article is specifically about Open Directory binding/authentication problems, which have not been established on this Mac mini; it is not yet a confirmed fix for this Guest-signing failure. SMB2-only also removes SMB3 support and associated security features. An additional community-reported workaround is the macOS server preference `SigningRequired=false` in `/Library/Preferences/SystemConfiguration/com.apple.smb.server`; Apple documents it only in an archived article for older macOS versions; it was later tested and worked (see [the server change](#mac-mini-signing-change-2026-10-12)). After the server change, the TV successfully listed and read photos during manual preview. Its DreamService started on idle and displayed the first SMB photo. Multi-photo progression and HEIC rendering in dream mode remain to be verified. The bundled sample-photo preview still works after moving source listing and decoding to the background.

### Mac mini signing change (2026-10-12)

The cause was server-side. In SMBJ 0.15.0, a session requires signing when either the client config or the server's NEGOTIATE `SecurityMode` requires it. A Guest session with signing required throws `SMB2GuestSigningRequiredException`. `withSigningRequired(false)` only clears the client half, so no client option could avoid it. An unauthenticated NEGOTIATE probe (`tools/check_smb_signing.py`) showed the Mac mini reporting signing as required at SMB 3.0.2. Apple's own client still mounted the share as Guest, so macOS tolerates unsigned Guest sessions despite advertising the requirement.

Apple does document the server preference, in an archived article that applies to macOS 10.13.3 and earlier: [Turn off packet signing for SMB 2 and SMB 3 connections](https://support.apple.com/en-us/101442). It still works on the current macOS when applied with Apple's sequence. Writing the key and running `launchctl kickstart -k system/com.apple.smbd` was not enough. On the Mac mini (user-operated, with the original plist backed up first):

```sh
sudo launchctl disable system/com.apple.smbd
sudo launchctl bootout system/com.apple.smbd
sudo defaults write /Library/Preferences/SystemConfiguration/com.apple.smb.server SigningRequired -bool false
sudo /usr/libexec/smb-sync-preferences
sudo launchctl enable system/com.apple.smbd
sudo launchctl bootstrap system /System/Library/LaunchDaemons/com.apple.smbd.plist
```

The probe then reported `SIGNING_REQUIRED=False`, and the unchanged TV build displayed photos from the share through SMBJ's explicit Guest mode. The user accepted the trade-off: the change applies to every SMB client of the Mac mini, and sessions are unsigned, on the basis that the share is read-only and reachable only on the home LAN. A macOS update may restore the default. Rerun the probe if the TV source stops connecting. To revert, run `sudo defaults delete /Library/Preferences/SystemConfiguration/com.apple.smb.server SigningRequired` within the same stop, sync, and start sequence. The dedicated read-only account remains the fallback if the preference stops working.

## Product implication

“All photos” and “live album sync” are goals, not promises for both providers. The app must show capabilities per source honestly. For this private setup, build the local slideshow first, then use read-only SMB access to available originals (see [what originals contains](#what-originals-contains)). Album selection builds a metadata-only catalog on the TV from a locally staged read-only Photos database snapshot and points to existing readable originals; it does not export or duplicate photo files. Do not infer albums from package directories. Shared albums need a separate storage-mapping result before they can be included. Google Picker remains an optional limited-selection path.

For **Location + date** labels, EXIF GPS coordinates are sent to Android's built-in Geocoder for a best-effort place name. This may involve Android's network-backed geocoding provider, so place-name availability and accuracy depend on the TV and its connectivity. A missing provider, empty result, timeout, or lookup error leaves the existing coordinate label in place. Date-only and no-label modes never request geocoding. Results are cached in memory for the current preview or dream run; no photo coordinates or resolved names are persisted by this feature. Android 12/API 31 uses the older blocking API on a separate background executor; API 33 and later use the callback API. [Android Geocoder reference](https://developer.android.com/reference/android/location/Geocoder)

During the TCL TV check, Android's platform EXIF reader returned no GPS or date from two real SMB JPEGs when given SMBJ's network stream directly, although the Mac read their EXIF records. Reading at most the first 512 KiB into a memory stream before EXIF parsing restored both fields on the TV for the tested JPEG. The bytes are discarded after each label is built; no photo file is saved on the TV by this path. This is a bounded best-effort read, so metadata beyond the prefix may still be unavailable. See [device findings](DEVICE_TESTING.md#device-findings).

- **Resolution (long edge):** 2,104 are 1080p-class (1920×1080 is the most common size), 907 are 720p-class, 336 are smaller, and 7 are 4K or larger.
- **Duration:** median 31.6 s, 90th percentile 110 s, 99th percentile 500 s, longest 2,994 s; 52.6 hours in total. 1,590 are under 30 s, 2,543 are 60 s or shorter, and 27 are over 10 minutes.
- **Flags:** 632 are marked HDR (type 5); in the sample these were HLG with Dolby Vision metadata. 653 carry subtype codes 100–103 (not mapped to Photos' names; the sample included 120 and 240 fps clips).
- **Shared-album copies:** 591 of the videos (18%) are iCloud Shared Album assets (`ZSAVEDASSETTYPE` 4) stored under `<id>/<album GUID>` folders that are not in `originals` on the clone; catalog v3 excludes them, leaving 2,667 usable videos.
- **Not usable as catalog videos:** 65 of the 3,354 active videos are stored outside `originals` (an absolute directory) and 35 have no recorded file size, so catalog v2 listed 3,258 videos from a newer database state; v3 drops the shared-album copies above (see [media type](MEDIA_TYPE.md#catalog-v2)).
- **Sample formats:** H.264 14, HEVC 8 (4 Main 10 HLG with Dolby Vision), Motion JPEG 4, MPEG-4 Part 2 2. Audio: AAC 20 (one HE-AAC), PCM 4, AMR-NB 1, none 3. Frame rates from 14 to 240 fps; 6 clips carry rotation metadata (portrait). Video bitrate ranged from 0.43 to 70.8 Mbps with a median of 7.7 Mbps.

### Video permissions (2026-10-17)

`make_photos_readable.sh` handles only photo extensions (jpg, jpeg, png, webp, heic, heif), so videos keep the owner-only (`0600`) mode the Photos library gives them. In the 28-video sample from the clone, 8 were world-readable and 20 were owner-only. Among the 400 highest-bitrate videos of 5–60 s, 138 were readable and 250 were owner-only; every clip above 18.4 Mbps in that set was owner-only, including all 4K and slow-motion files. Until videos are made readable, Guest can play only the older minority. Making them readable extends the accepted consequence in [product](PRODUCT.md) (any account or LAN device that can reach the Guest share can read them) from photos to videos, so it needs a recorded product decision before the script changes.

**Update (2026-10-17):** `make_photos_readable.sh` now covers video extensions too (decision in [product](PRODUCT.md)). Tested on a fake library in scratch: `scan` and `apply` handled photos and all five video types, left a `.dng`, a `.txt`, and the database untouched, ignored an already-readable video, `revert` restored exactly the changed files, `INCLUDE_VIDEOS=0` gave the old photos-only behavior, and the CCC (root) path worked. On the real library (run by the user on the Mac mini, 2026-10-17): the live library had 2,436 unreadable files (2,227 `.mov`, 177 `.mp4`, 21 `.jpeg`, 4 `.avi`, 3 `.heic`, 2 `.3gp`, 2 `.png`); `apply` reported `found=2436 still_unreadable=0 chmod_error=0`. The user also ran `apply` directly against the clone volume, which found the same 2,436 files, so CCC had not yet carried the new modes over; the clone was readable after that. Afterwards 28 of 28 sampled videos were world-readable on the clone. Running the script against the clone is a one-off exception to "never writes to the clone".

## Excluding screenshots, documents, and receipts (2026-10-18)

The user does not want screenshots, documents, or receipts in the slideshow ([product](PRODUCT.md)). Random "All" mode only walks the `originals` tree, so the exclusion list has to come from the Photos database, which the TV already stages for album selection. Photos classifies photos itself in the background and its Utilities albums (Documents, Receipts) are built from that; the app reads the same classification instead of guessing from pixels.

**Where the signals are** (clone's `Photos.sqlite`, last checkpoint, read-only; counts only, no filenames):

- `ZASSET.ZISDETECTEDSCREENSHOT = 1`: 832 of 34,526 active photos (2.4%).
- `ZSCENECLASSIFICATION` rows with `ZCLASSIFICATIONTYPE = 0` hold one scene id and a confidence per asset (`ZASSETATTRIBUTES` joins `ZADDITIONALASSETATTRIBUTES.Z_PK`, whose `ZASSET` is the asset key). Apple's scene taxonomy ships on macOS (`PhotosFormats.framework/Resources/PFSceneTaxonomyData_99.bz2`, plain text once decompressed) and names the ids: 492 document, 1086 receipt (a child of document), 1665 screenshot, 1664 handwriting, 1494 whiteboard. Versions 84 and 99 agree on these ids. The library's scene analysis versions are 100 and 101, newer than either file, so the ids were also checked by looking at photos (below).
- Not usable: rows of `ZCLASSIFICATIONTYPE = 3` (content classification, whose taxonomy names document, driving licence, passport, visa) hang off video attributes: 2,224 of the 2,437 assets they cover are videos, and the counts (1,797 "driving licences") are not plausible for photos. They are ignored.
- Coverage gap: 9,945 of the library's 37,968 asset-attribute rows have scene analysis version 0, meaning they were never analyzed. A photo with no classification cannot be excluded.

**Calibration** (26,214 active, non-hidden, non-shared photos). Counts by rule: document confidence ≥ 0.2 2,778; ≥ 0.4 2,375; ≥ 0.6 2,009; receipt ≥ 0.19 192; screenshot flag 832. Random samples of 24 per band, viewed as contact sheets (thumbnails were deleted afterwards):

| Band | What the sample showed |
| --- | --- |
| document ≥ 0.6 | 24 of 24 documents, receipts, notes, or whiteboards |
| document 0.4 to 0.6 | about 21 of 24 documents or forms; 3 photos of people or a display |
| document 0.2 to 0.4 | about 12 of 24 real documents (licence, passport, forms); the rest family photos |
| document 0.1 to 0.2 | mostly ordinary photos; about 4 of 24 ID cards, a few maps and signs |
| receipt ≥ 0.19 | 24 of 24 receipts |
| screenshot flag | 12 of 12 screens (a few are photos of a screen) |
| no tag (control) | 24 of 24 ordinary photos |

**Rule used:** exclude a photo when the screenshot flag is set, or document confidence is ≥ 0.4, or receipt confidence is ≥ 0.19. That is 2,458 photos, 9.4% of the 26,214. The constants are in `PhotosAlbumCatalog.kt` and need a catalog refresh to change. Known limits: ID cards and some real documents below 0.4 still show, a few ordinary photos at 0.4 to 0.6 are hidden, and unanalyzed or newly imported photos are not filtered until Photos has analyzed them and the TV catalog is refreshed.

**How the TV uses it.** Catalog version 4 added `excluded`, the relative paths of those photos, and drops them from every album's `paths` (so album counts and covers never include them). Version 6 keeps those classification exclusions for trashed assets too: Photos may leave a deleted asset's original in the tree that *All* mode walks, so trash state must not remove its exclusion. This does not change which assets are included in albums or the portrait list. *All* mode skips excluded paths while walking the tree, before sampling; album mode filters again at load time as a guard. If no usable catalog exists the slideshow shows everything and logs a warning. The query remains one uncorrelated subquery, a single pass over the classification rows. Run on the Mac over SMB it took 134 s; the TV's timing is recorded in [device testing](DEVICE_TESTING.md#excluding-screenshots-documents-and-receipts-2026-10-18).
