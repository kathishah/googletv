# SMB regular-album selection

## Phase 1 scope

Let the user choose one or more regular, user-created albums from the Mac Photos library for the TV slideshow. The TV reads existing supported image files over the SMB share; it does not export or duplicate photos. Shared albums are explicitly deferred to a later phase and do not appear in this picker. Their path investigation does not block implementation or release of regular-album selection.

For this phase, “album” means a regular user-created Photos album whose assets can be mapped to existing readable files under the library's `originals` directory. Smart albums, folders, Shared Albums, and videos are out of scope unless validation shows they can be supported cleanly and the product scope is updated.

## User experience

1. Keep **All photos** as the default, preserving today's behavior. The main settings screen is a compact two-column table: setting name at left and D-pad choices at right. Its rows are **Photo source** (Sample pics, SMB share, SMB settings), **Photos** (All, Choose Albums), **Pool** (100, 250, 500, 1,000), **Interval** (10 secs, 30 secs, 1 min, 5 min, 15 min), and **Label** (Location + date, None). The Pool row stays visible but its choices are disabled in Choose Albums mode; they apply only to All. Main-screen **Save** commits the settings draft and **Cancel** restores the last saved values.
2. **SMB settings** opens a separate screen with the saved IP address, share name, and library path prefilled and editable. **Back** returns to the settings table with edits staged; the main-screen Save or Cancel commits or discards them.
3. **Choose Albums** opens the picker and activates album mode. Album selection changes save immediately; the settings table summarizes the saved choice. Switching back to All preserves album IDs for later use.
4. **Choose albums** opens a full-screen, D-pad-friendly horizontal carousel of regular albums. Do not include a search bar or show Shared Albums, disabled shared cards, or a Type filter in Phase 1. Use full-card cover images with a compact title and picture count overlaid on a dark gradient. If no readable cover exists, use a neutral cover without hiding the album. The first five visible covers are prefetched; cover thumbnails use an app-private persistent cache so later visits can show them without another SMB read.
5. Provide top-rail controls for **Refresh**, **Sort** (newest year-month first by default, or A–Z), **Select all**, and **Clear all**. Albums with the same year-month sort by title; albums without a usable year-month follow dated albums, sorted alphabetically. A focused card has a clear outline independent of its selected checkmark. The bottom rail shows selected album and distinct picture totals, a saved-automatically hint, and **Done**; remote Back also returns to settings. Every album toggle and bulk selection saves immediately. Preserve selected IDs if the catalog is missing or invalid, and show an actionable warning for IDs no longer present. When multiple selected albums contain the same file, include it once. Use all usable photos from selected albums and shuffle the full set without a fixed pool-size limit. The random-pool setting applies only in **All** mode.
7. In **Choose Albums** mode, settings summarizes the saved choice (for example, “3 albums · 842 photos”) and allows reopening the picker. Preview and DreamService use the same persisted mode and selection. Persist the mode separately from album IDs so an empty or invalid album selection can never be interpreted as **All photos**.
8. Selecting **Choose Albums** opens the picker screen immediately. Show an in-screen spinner/status area while loading the local catalog or doing the first database read; do not navigate to a separate build/cache screen. Enumerate the current step (for example, reading the saved catalog, connecting to the share, copying the database, reading albums, validating photo paths, or saving the catalog). With a valid local catalog, render the album carousel as soon as it is read; do not wait for a network request. On first use, or when the user selects **Refresh**, read the cloned Photos SQLite database over SMB, build a metadata-only JSON catalog in persistent app-private storage, then render the carousel. Reopening uses the cached catalog without rereading SQLite. The carousel's top rail provides a D-pad accessible **Refresh** action.
9. Refresh runs in the same picker screen with step/progress feedback. Keep the old carousel usable if practical, and keep the old catalog until a replacement has been fully built and validated. If refresh fails while a valid cache exists, retain the old catalog and show an inline error. If no valid catalog exists, show an actionable error and retry/back choices. Preserve saved album IDs and never silently switch to **All photos**. If a refreshed catalog no longer contains a selected album, preserve that ID and explain that the selection is unavailable.
10. If a selected album contains no usable photos, keep it selected and explain that no readable supported photos are currently available. Keep **All photos** available as an explicit mode.

## TV-cached regular-album index contract

- On first **Choose albums** use, or after explicit refresh, the TV obtains `Photos Library.photoslibrary/database/Photos.sqlite` over the existing read-only SMB connection. SQLite must query a local staged copy; do not open the database as a live SQLite file over SMB. Copy any required matching SQLite WAL companion files as one consistent snapshot. Open the staged copy read-only/query-only, query it, then discard the staging copy after the app catalog is safely written. Never modify the Photos package or export/copy photo files.
- Store the resulting metadata-only JSON catalog atomically in persistent app-private storage, separate from evictable temporary cache. Suggested schema: `version`, `pathRoot: "Photos Library.photoslibrary/originals"`, `createdAt`, and `albums`; each album has `id`, `title`, optional `yearMonth` (`YYYY-MM`), `photoCount`, and safe paths relative to `originals`. The cached JSON is private to the TV app; there is no JSON sidecar on the SMB share and no Mac-side index generator in the user workflow.
- Reopening the picker reads the local JSON catalog only. **Refresh** replaces it only after a complete successful read/query/validation. A failed refresh preserves the prior valid catalog and selected IDs. If cache is lost or invalid, the next picker open rebuilds it from SQLite; if SMB is unavailable then, show an actionable error and preserve selection.
- Album IDs are opaque `ZGENERICALBUM.ZUUID` values. The current clone has a UUID per regular album; identity is independent of title and row ordering. Photos uses a private, changeable schema, and UUID continuity still needs checking after an actual CCC refresh.
- The TV query initially includes regular user-created albums only. It maps membership to existing files under `Photos Library.photoslibrary/originals`. Video assets are excluded until the separate media-type feature is implemented. Current source behavior shows original, unedited files; album selection does not apply Photos edits.
- The TV validates that each path remains under the configured library-package root and specifically under `originals`, exists, is readable, and has a supported image type. It does not recursively scan internal directories or present them as albums. Duplicate paths are collapsed. Missing, unsupported, duplicate, and out-of-root references are reflected in usable counts and diagnostics without logging photo filenames.
- If an index refresh removes a selected album ID, keep the saved ID and tell the user that selection is unavailable. Do not broaden the slideshow silently. The user can remove the unavailable selection or explicitly return to **All photos**.
- Album cover tiles use a bounded, display-sized decode of a representative existing album image. They are previews only; no exported image copies are created. Photo filenames and host addresses stay out of logs.

## Progress so far

The initial two references were supplemented by a 24-album spot sample: 22 references resolved to readable supported files under `originals`; two were unsupported or video; none were missing/unreadable or out of root. The full clone scan found 33,302 usable membership references, 4,010 unsupported or video references, 3 missing files, 1,116 out-of-root references, and no unreadable files or within-album duplicate paths. Those 33,302 references deduplicate to 15,091 usable paths, with 11,041 paths shared by multiple albums. The complete sample catalog was generated and schema-checked at `/tmp/PhotosAlbumIndex.json`. The TV implementation stages SQLite/WAL read-only, builds and reuses a persistent catalog, and is now installed on the TCL. A cached catalog and thumbnails have been displayed on the device. The user reports a successful full refresh in an earlier manual session; no fresh database transfer was run during the carousel UI update.

Build and device verification (2026-10-17): `:app:assembleDebug` succeeded with Android Studio's bundled Java and the installed SDK. The APK was installed and launched on the TCL; the picker was opened from settings and the cached catalog and album covers were visible. Back and re-entry returned to the saved catalog and reused cached covers. The user approved the carousel UI direction. Do not infer DreamService album-mode success from this launcher-screen check.

## Refresh performance investigation

Refresh performance is the next open investigation, separate from the implemented carousel and local cache. Known observations and baseline measurements:

1. The mounted clone measured `Photos.sqlite` at 1,280,086,016 bytes and `Photos.sqlite-wal` at 6,370,653,032 bytes (7,650,739,048 bytes total; 7.12 GiB). The user observed the TV copy at about 7% after roughly one minute, then later reported completing a full refresh. This was not a controlled throughput measurement.
2. On the development Mac, a 128 MiB sequential WAL read took 12.705 s (10.56 MB/s); a straight-line extrapolation is about 12.1 minutes for the database/WAL pair, not a TV measurement. Two concurrent 64 MiB reads (one from each file) took 17.3 s overall (about 7.8 MB/s combined), slower than that sequential sample.
3. The TCL reported a 780 Mbps Wi-Fi link rate, which is a negotiated link rate rather than measured SMB throughput. App storage showed 44 GiB available, so the measured file pair fits, but storage capacity does not explain transfer time.
4. On a picker re-entry, “Reading the saved catalog from this TV…” remained on screen for several seconds before the carousel appeared. This was a rough observation, not a timed benchmark; no SMB copy was requested on that visit. It suggests separately measuring local JSON read/parse and album-card construction too.

Next, collect repeatable TV timings for database and WAL copy, SQLite query, path validation/readability checks, catalog serialization/write, cached catalog read/parse, and cover loading. Keep a stable clone snapshot during comparisons. Check SMB read buffering/request size, protocol overhead, per-file metadata operations, TV storage throughput, and catalog JSON size. Compare parallel reads against the existing sequential sample; do not assume parallel copy helps, and preserve the matching DB/WAL snapshot if CCC is refreshing. Keep progress reporting tied to actual bytes and report phase changes separately. Record measured bytes and elapsed times without logging photo filenames or host addresses.

## Later phase: shared albums

Shared Albums created by the user or shared with the user remain a separate later phase. They are not shown or selectable in Phase 1. Current probes show inconsistent path materialization: initial samples did not resolve; later probes found 7 readable paths in two albums, and saving two Arizona items was followed by a count of 14. These counts do not identify which items changed or why, and basename-only matching produced unrelated results. Next, map role values to actual Photos UI albums, compare the live library and the correct CCC clone, trace shared item/resource relations to exact readable files, and use controlled before/after saves of known items to identify what changes. Require repeatable mappings for both albums created by the user and albums shared with the user, including SMB readability, before adding shared cards or the Type filter. See [shared-album probe findings](PHOTO_SOURCES.md#album-database-probe-2026-10-16).
