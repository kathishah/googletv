# Roadmap

Milestones are in order. Each has an exit condition; do not start the next milestone until it is met or the gap is recorded in [device testing](DEVICE_TESTING.md#device-findings).

## Current work order

1. **Reconcile documentation and close source-operation questions.** Keep the HEIC permission/decode findings consistent across docs. The Mac mini uses Download Originals; the permission script and CCC clone run daily, with the script first. Full live-library/clone content equality remains unverified and is recorded as an open verification gap.
2. **Correct photo orientation.** Done: apply EXIF orientation in the shared decode path. Two portrait 12 MP HEICs selected from the recreated first-25 sample set displayed upright on the TV; 24 MP decoding remains a separate item below.
3. **Soften label rendering.** Done: photo labels use 85% text opacity and 44% shadow opacity; status messages remain fully opaque. Reviewed in the TV preview and confirmed the label stayed readable with a softer appearance.
4. **Integrate 24 MP HEIC playback.** Done for the tested sample set. The app routes large HEIF grids through the pinned libheif/libde265 tile decoder, retains Android decoding for other images, and preloads one upcoming slide while the current photo remains visible. A targeted two-image preview on the TCL verified 5712×4284 landscape and 4284×5712 portrait HEICs through the production SMB and native decoder path. Four successful decodes took 5.5–6.5 seconds, and the images advanced without a blank/loading screen. A three-minute local-file soak showed 94–111 MB process PSS and 36–44 MB native heap across 15 samples, with five successful decoder completions and no photo errors; this is an initial stability check, not a long-duration memory certification. Production decoder output matched all six colors in a Rec. 709 chart, and six orientation variants (0/90/180/270 degrees, horizontal flip, vertical flip) returned the exact expected color positions. Continue with broader real-photo color review if issues appear; proceed to TV integration checks.
5. **Finish TV integration checks.** Full-screen T-Exhibition artwork remained active for over two minutes with Google Backdrop selected, both with Keep Screen On enabled and temporarily disabled; no Google Ambient takeover occurred. The app DreamService activated and advanced with bundled photos during idle, while an SMB-backed attempt hit the intermittent listing failure. No TCL Auto Launch control was found in Android App Info or app-ops. Date-only rendering passed on a temporary EXIF-tagged bundled sample. Done: no separate Auto Launch control was found and none was needed, the user reports the Auto Launch question is resolved, and activation was observed at the default 600000 ms timeout and after a TV restart (the latter user-reported). The intermittent SMB listing failure was mitigated (item 6). Details are in [device testing](DEVICE_TESTING.md#device-findings).
6. **Make SMB playback resilient.** Done for network blips, root cause still open. Transient SMB errors (connection, timeout, dropped session) no longer end a dream session or remove photos: the listing retries with 2/4/8/15 s backoff, one SMB connection is reused, and only per-photo errors drop a photo. After 3 consecutive failures the app shows three stored public-domain artworks captioned "SMB failure. Loading…" until SMB reads work again. Verified on the TCL by turning Wi-Fi off at dream start and mid-play, plus 11 clean idle dream starts. The earlier intermittent listing failure did not reproduce under logging, so its cause is unrecorded; the hardened build logs the exception chain if it recurs (see [device testing](DEVICE_TESTING.md#device-findings)). The user closed this item as sufficient. The dream still lists the whole tree at each start (3–4 s) instead of using a saved index; that remains an optional follow-up feature.
7. **Regular album selection.** Implemented in Android: compact settings table, separate SMB settings screen, explicit All/Choose Albums mode, staged read-only SQLite/WAL copy with combined-byte progress, regular-album query, atomic app-private JSON catalog and reuse, explicit Refresh, and a horizontal carousel with immediate selection saves, persistent cover thumbnails, D-pad focus outline, and Done/Back return. The debug APK builds and is installed on the TCL. The cached catalog and thumbnails were displayed on the TV, and the user approved the picker direction. A new database transfer/refresh was not run during this UI update. Shared Albums and the Type filter remain deferred. Clone mapping validation found 33,302 supported membership references (15,091 unique paths), 4,010 unsupported/video, 3 missing, and 1,116 outside `originals`. See [album selection](ALBUM_SELECTION.md).
8. **Measure and improve album refresh time.** Done for the first round (2026-10-17). The 6.4 GB WAL is required (the clone's DB is about 11 days older than its WAL), so the TV now keeps a persistent staged database and WAL and resyncs incrementally: only WAL bytes after the last committed frame are fetched, and a refresh that finds the library unchanged keeps the saved catalog without querying. On the TCL: first full refresh 900.7 s (98% SMB transfer at about 9 MB/s), later refresh with nothing to fetch 45.9 s (of which SQLite's first read building the WAL index is 37.4 s), unchanged shortcut 3 s. See [album selection](ALBUM_SELECTION.md#measured-refresh-timings-tcl-2026-10-17). After the next CCC run the incremental path was measured with real growth: 60.7 MB of new WAL fetched, refresh 50.6 s, and the saved selection still worked. Open: `-shm` reuse, consistency during a live CCC refresh, and the optional Mac-side compact index (CCC hook only; launchd is blocked by TCC).
9. **Add media-type selection.** Spec drafted 2026-10-17: [MEDIA_TYPE.md](MEDIA_TYPE.md), with a [mock](mockups/media-type.html). Photos only (default), photos and videos, or videos only, in both All and Choose albums, in the in-app slideshow. The DreamService never plays videos; with Type other than Photos it shows 500 random photos. Videos play muted and letterboxed for their own length (cap 60 s) through one progressive-download reader. Groundwork done: library and TCL decode surveys, SMB playback tests (typical clips stream with no stalls; 71 and 89 Mbps clips need a start wait), and the permission script extended to videos. Seven milestones, each with a TV exit check; milestone 1 (catalog v2 and counts) is next. Five decisions are open for confirmation in the spec.
10. **Add multi-image layouts.** Let the user choose a randomized two-image side-by-side layout or four-image tile layout. Evaluate crop/fit behavior, mixed aspect ratios, labels, and performance with large HEIC images.
11. **Other later work.** Saved file index, Google Photos, and visual transitions remain optional follow-up features.

## Feature feasibility: album selection

**Assessment: regular-album mapping and the TV cache flow are implemented; on-device cache reuse is observed, with refreshed-database transfer and live-refresh consistency still open. Shared-album support is deferred.** The read-only full clone scan mapped 33,302 supported membership references; 1,116 references were out of `originals`, 3 were missing, and 4,010 were unsupported or video. The TV queries a staged local copy on first use or explicit refresh and persists the derived catalog; the cached catalog and cover thumbnails have been shown on the TCL. See [album mapping and TV cache findings](PHOTO_SOURCES.md#phase-1-regular-album-cache). Photos uses a private, changeable schema and the clone may lag the live library; query failures must preserve any prior valid cache and selection.

Phase 1 uses a **TV-cached metadata-only regular-album catalog** built from the Photos SQLite database. It contains regular album names and references to corresponding existing original files; it does not export or duplicate photos. The TV reads SQLite over SMB only when no valid cache exists or the user explicitly refreshes, stages it locally for read-only querying, and atomically stores the derived JSON catalog in app-private storage. It lets the user select one or more regular albums, then shuffles all usable, deduplicated matched paths without a fixed pool-size cap. The existing random-pool limit applies only to **All photos** mode. Validate regular-album links, stable IDs, path containment, duplicates, missing files, hidden/deleted assets, edits/multiple resources, stale clone state, database/WAL snapshot handling, and refresh behavior before relying on the mapping. Do not use filenames alone as global identifiers. Shared album mapping is a separate later phase.

Shared album path feasibility remains a separate investigation and does not block Phase 1. The current samples are inconsistent: initial references failed to resolve, then later probes found 7 and 14 distinct readable paths in different albums after the user saved selected items. These counts test existing DB paths and do not establish which item was saved or why more files resolve. Continue read-only investigation, but keep this out of the regular-album implementation exit criteria. Details are in the [album database probe](PHOTO_SOURCES.md#album-database-probe-2026-10-16).
