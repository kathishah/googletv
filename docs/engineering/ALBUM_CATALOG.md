# Album catalog and sync (design)

Product behavior (scope, the picker, refresh and error states) is in [product](../PRODUCT.md#album-picker). This document is the design: the TV-cached catalog contract, the incremental sync of the Photos database, and the shared-album investigation. How it was built, with the checks that were still open at the time, is in the journal: [progress](../../journal/2026-10-17-1455-album-selection-progress.md) and [remaining checks](../../journal/2026-10-17-1455-album-selection-remaining-checks.md).

## TV-cached regular-album index contract

- On first **Choose albums** use, or after explicit refresh, the TV syncs `Photos Library.photoslibrary/database/Photos.sqlite` and its `-wal` file over the existing read-only SMB connection into a persistent app-private stage (`files/photos-db-stage`). The stage state carries a private source ID; a staged copy from another configured SMB location is not reused. An unbound stage from earlier builds is adopted once by the currently configured source (the app supports one library). SQLite must query that local copy; do not open the database as a live SQLite file over SMB. The stage is kept between refreshes and resynced incrementally (see [incremental sync](#incremental-wal-sync-implemented-2026-10-17)). Open the staged copy read-only/query-only, delete any stale `-shm` first, and query it. Never modify the Photos package or export/copy photo files.
- Store the resulting metadata-only JSON catalog atomically in persistent app-private storage, separate from evictable temporary cache. Schema (version 8; version 3 changed the video list, version 4 added `excluded`, version 5 added `portrait`, version 6 retains exclusions for trashed originals, version 7 binds the SQLite snapshot, and version 8 binds one SMB source): `version`, private `sourceId`, `pathRoot: "Photos Library.photoslibrary/originals"`, `createdAt`, optional `sourceModifiedAt`, `sourceSnapshotIdentity`, `albums`, `videos`, `excluded`, and `portrait`. `sourceId` is a SHA-256 hash of the normalized SMB host, share, and library path; it does not expose those values. Catalog reads reject a different source ID. `excluded` contains safe relative paths of screenshots, documents, and receipts, which are also left out of every album's `paths` (see [exclusion entry](../../journal/2026-10-18-1219-excluding-screenshots-documents-receipts.md)); each album has `id`, `title`, optional `yearMonth` (`YYYY-MM`), `photoCount`, `videoCount`, `paths` (photos, safe paths relative to `originals`), and `videos` (`p`, `d`, `s`). See [media type](VIDEO_PLAYBACK.md#catalog) and [portrait pairs](PORTRAIT_PAIRS.md#data). The cached JSON is private to the TV app; there is no JSON sidecar on the SMB share and no Mac-side index generator in the user workflow.
- Reopening the picker reads the local JSON catalog only. **Refresh** replaces it only after a complete successful read/query/validation. A failed refresh preserves the prior valid catalog, carousel and selected IDs, and shows an inline error with **Retry**. If no valid catalog exists, show an actionable full-screen error and keep selection. If cache is lost or invalid, the next picker open rebuilds it from SQLite; if SMB is unavailable then, show an actionable error and preserve selection.
- Album IDs are opaque `ZGENERICALBUM.ZUUID` values. The current clone has a UUID per regular album; identity is independent of title and row ordering. Continuity was observed across an actual CCC refresh when the saved selection still worked, and UUID continuity has been verified (user-confirmed 2026-10-19). Photos uses a private, changeable schema, so this does not establish future compatibility.
- The TV query includes regular user-created albums and maps membership to existing files under `Photos Library.photoslibrary/originals`. The catalog stores photos and video membership; the Type setting filters what is shown or played ([media type](VIDEO_PLAYBACK.md)). Current source behavior shows original, unedited files; album selection does not apply Photos edits.
- Catalog building validates relative-path syntax, containment under the configured library-package root and `originals`, and supported path types; it does not open every referenced file to prove existence or readability. At playback start, a sample of up to eight photos is opened. Catalog candidate counts therefore differ from the verified-readable startup sample. The app does not recursively scan internal directories or present them as albums. Duplicate paths are collapsed. Missing, unsupported, duplicate, and out-of-root references are reflected in usable counts and diagnostics without logging photo filenames.
- If an index refresh removes a selected album ID, keep the saved ID and tell the user that selection is unavailable. Do not broaden the slideshow silently. The user can remove the unavailable selection or explicitly return to **All photos**.
- Album cover tiles use a bounded, display-sized decode of a representative existing album image. They are previews only; no exported image copies are created. Photo filenames and host addresses stay out of logs.
- Album cover files live in a source-ID-specific private folder, and album selection preferences carry the same source ID. If the configured SMB location changes, the old album IDs are not applied to it; choose albums again for the new location. The single-library migration binds the previous selection to the existing configured SMB location on first launch.

## Incremental WAL sync (implemented 2026-10-17)

- **State:** `DatabaseStage` keeps `Photos.sqlite`, `Photos.sqlite-wal`, and `sync-state.properties` (database size and modification time, WAL header hex, committed WAL bytes). State is written only after a verified copy and removed before the database file is replaced.
- **Reuse rule:** if the remote database size and mtime are unchanged and the WAL's 32-byte header (including salts) is identical, only the WAL after the last committed frame is fetched. Otherwise the affected file is recopied in full. The last commit frame's header already on the TV must equal the one on the share, and the local WAL length must equal the recorded committed length.
- **Committed prefix:** `WalFrameScanner` walks the WAL as it streams and tracks the end of the last commit frame whose salts match the header. Uncommitted or old-generation frames after it are not kept, so a rolled-back tail is refetched next time. The WAL header checksum and every complete frame's cumulative checksum are validated while streaming (SQLite's byte order); a checksum-invalid log aborts the refresh and keeps the old catalog, and an incremental resume seeds the running checksum from the saved committed frame.
- **Safety:** the database and WAL header are re-read after the copy; a change fails the refresh with an actionable message and leaves the old catalog. A failed query clears the stage so the next refresh starts clean. The `-shm` index is deleted before every query because a retained one would hide appended frames.
- **Unchanged shortcut:** if the sync fetched nothing and the saved catalog's `sourceModifiedAt` equals the newest database/WAL mtime, the saved catalog is kept without querying. Bump `PhotosAlbumCatalog.VERSION` whenever the query or path mapping changes. The picker subtitle shows "Library data as of" that time.
- **Cost:** about 7.1 GiB of persistent TV storage (44 GiB was free). Concurrent syncs in the app process are serialized.
- **Why the WAL is copied.** The main database file changes only when Photos checkpoints; on the clone it was about 11 days older than the WAL, so a database-only copy would show an old library ([investigation](../../journal/2026-10-17-1455-album-refresh-performance-investigation.md)).
- **Measured on the TCL.** First full refresh 900.7 s (98% SMB transfer at about 9 MB/s); refresh after real CCC growth (60.7 MB of new WAL) 50.6 s; unchanged library 3 s ([all timings](../../journal/2026-10-17-1617-album-refresh-timings.md)).

## Later phase: shared albums

Shared Albums created by the user or shared with the user remain a separate later phase. They are not shown or selectable in the picker. Current probes show inconsistent path materialization: initial samples did not resolve; later probes found 7 readable paths in two albums, and saving two items from one of them was followed by a count of 14. These counts do not identify which items changed or why, and basename-only matching produced unrelated results. Next, map role values to actual Photos UI albums, compare the live library and the correct CCC clone, trace shared item/resource relations to exact readable files, and use controlled before/after saves of known items to identify what changes. Require repeatable mappings for both albums created by the user and albums shared with the user, including SMB readability, before adding shared cards or the Type filter. See [shared-album probe findings](../../journal/2026-10-16-2354-shared-album-probes.md).
