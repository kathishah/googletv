# Clone ownership and the library-wide permission change (2026-10-13)

Moved verbatim from `docs/PHOTO_SOURCES.md` on 2026-10-19, with links updated for the new location. Inline corrections and updates are kept as originally written.

The Mac mini's Photos settings screenshot shows the open library under `Samsung_T5/…/Pictures/Photos Library.photoslibrary`; **Correction (2026-10-13):** the package reached through the SMB `Photos` share is **not** that live library. It is a cloned copy on a second external drive on the Mac mini. The user expects it to contain exactly the same files as the live library; this has not been verified. Identical file contents do not guarantee identical ownership or modes. The clone is made with Carbon Copy Cloner (CCC). Per Bombich's documentation, CCC preserves source ownership and permissions by default unless the task's "Don't preserve permissions" option is checked ([Bombich](https://bombich.com/en/kb/ccc/5/best-practices-updating-your-macs-os)). It also expects ownership to be enabled on the destination volume ([Bombich](https://bombich.com/en/kb/ccc/3/using-carbon-copy-cloner-backup-another-macintosh-your-network)). **Confirmed on the Mac mini (2026-10-13):** the 0600 modes originate in the live library, and CCC copies them faithfully. Twenty-five HEIC files in the clone were all 0600, and so were the same 25 files in the live library. Of 25 JPEGs, 17 were 0600 and 8 were 0644 on both drives. All 50 had the same owner and identical bytes on both drives. The live `Samsung_T5` volume has ownership disabled: Disk Utility shows Owners Disabled, and the drive is mounted `noowners`. Photos therefore never sees the owner-only modes as a problem. The clone volume, which is the shared `Photos` volume, has ownership enabled, so SMB Guest is evaluated as "others" and denied. The user's umask is 0022. Ten sampled 0600 HEICs had no ACLs. Their extended-attribute names were identical on both drives and included Photos `com.apple.assetsd.*` attributes, `com.apple.cpl.original`, `com.apple.assetsd.cloudAsset.UUID`, and `com.apple.quarantine`. Why Photos writes some originals as 0600 and others as 0644 is still unknown. The xattrs are suggestive of iCloud Photo Library involvement, but the 0644 files' xattrs have not been compared. Whether SMB Guest could read 0600 files if the clone volume ignored ownership is untested. Changing CCC's permission handling or the clone volume's ownership setting, adding a post-clone permission step, or using an export folder are product decisions for the user. A user-run trial made 25 HEICs 0644 in the live library with `chmod go+r`. Photos still displayed them, and the mode survived a Photos session. CCC propagated the mode to the clone, and the TV could then read and display them over Guest. Options beyond the storage layer are a Samba `force user` share or a Mac-side photo service running as the owner. Neither has been chosen or tested.

**Library-wide change (2026-10-13).** The user ran `zsh make_photos_readable.sh scan`, then `apply`, on the Mac mini, with Photos not running. `scan` found 18,601 supported photos that others could not read: 8,974 HEIC, 9,188 JPEG, 438 PNG, and 1 WebP. `apply` reported `found=18601 still_unreadable=0 chmod_error=0`, and a follow-up `scan` reported a total of 0. After the next CCC run, a `scan` pointed at the clone (`LIVE=<clone library> zsh make_photos_readable.sh scan`) also reported a total of 0. New photos imported later may again be 0600 until the script is re-run and the clone refreshed. The user now runs the permission script once a day before the daily CCC clone. Each apply records the changed paths on the Mac mini, so `revert` can undo exactly those files.

**Automation finding.** A launchd LaunchAgent running the script as the user could not read the external `Samsung_T5` volume. Its `diagnose` output showed `volume exists=yes dir=yes ls=Operation not permitted`, a macOS privacy (TCC) block on background access to the volume. The same checks succeeded from the user's ssh session. The agent was removed. The script also supports a Carbon Copy Cloner "before copying files" script mode: CCC runs it as root, it always exits 0, and it logs counts to `/Library/Logs/make_photos_readable.log`. Per [Bombich](https://support.bombich.com/hc/en-us/articles/21608812482455-Running-shell-scripts-before-and-after-the-backup-task), such a script must be a root-owned copy in CCC's Scripts folder, and a non-zero exit aborts the task. This mode is tested only on a fake library and is not installed; the user chose manual runs for now. An earlier note recorded the two as the same location. What the TV can show therefore depends on when the clone was last made and on how the cloning process sets file ownership and modes. The clone runs daily, after the daily permission-script run. The live and clone packages are expected to match, but full content equality has not been verified. Photos is set to **Download Originals to this Mac** (confirmed 2026-10-13), so Optimize Mac Storage is not the current concern for availability of local originals. Video support and 24 MP HEIC decoding still need separate device work before claiming full library coverage. [Optimize storage](https://support.apple.com/en-lamr/guide/photos/phta9b4673b4/mac).

The ordinary folders beside the package can be a separate SMB source later. Their folder names do not represent Photos albums.

Source-operation status (confirmed 2026-10-13): Photos uses **Download Originals to this Mac**; the permission script runs manually once a day before the daily CCC clone. Whether the clone contains every file from the live library remains unverified.
