# Shared album probes (2026-10-16)

Moved verbatim from `docs/PHOTO_SOURCES.md` on 2026-10-19, with links updated for the new location. Inline corrections and updates are kept as originally written.

Shared albums use a separate relationship: `ZSHARE`, with assets associated through `ZASSET.ZCOLLECTIONSHARE`. An expanded read-only clone sample tested 20 asset references from 20 distinct share groups, stratified across current-user role values 1 (9 references), 5 (9), and 6 (2). Each row had directory/filename metadata. All 20 referenced directories existed under `Photos Library.photoslibrary/scopes/cloudsharing/data/`, but all 20 were empty. None of the referenced files resolved under `originals` or at the expected `cloudsharing/data` path. A targeted, case-insensitive exact-basename search for those 20 filenames found no matches in the inspected `scopes/cloudsharing` or `resources/cpl` trees.

The user then ran [`probe_shared_album_paths.py`](../tools/probe_shared_album_paths.py) on the Mac mini against `/Volumes/Photos/Photos Library.photoslibrary`. It sampled one asset reference from up to 20 albums for each role value: 20/45 for code 1, 20/30 for code 5, and 2/2 for code 6. All 42 reported `parent exists=True`, `location=none`, and `not resolved`. This run did not repeat the tree-wide exact-basename search. The role values are from this private schema; interpreting them as owner/participant roles is not independently verified, so match the printed album titles against the Photos UI before assigning those meanings. Neither sample proves that shared media is absent from the library or unusable: files may be stored elsewhere or represented by a different resource mapping. Direct shared-album path resolution remains unresolved.

The user clarified that the intended album is `<album B>`; the earlier `<album A>` probe targeted the wrong album and should not be used to characterize album B. After saving album B to their library, the user ran the targeted probe against both the original library and the CCC clone. Each initially returned 72 shared-linked rows (71 photos, 1 video), matching the Photos UI, with directory and filename values on all rows and candidate parent directories present, but 0 exact files and 0 readable files at the tested locations. A recursive basename search found same-name files only under dated folders for 2011 or 2013; none plausibly matched the album B item dated December 17, 2025, demonstrating that basename matching alone is unsafe. The user then confirmed the target item appeared in the Photos Imports collection. A subsequent clone probe reported 7 of 72 exact file references found and readable under `cloudsharing/data`. Both commands shown for that run pointed to `/Volumes/Photos`, so they tested the clone twice. Updated probes on the original library then found 7 of 130 exact paths for `<album A>` and 7 of 72 for `<album B>`. In both albums, all seven were unique readable DB paths under `cloudsharing/data`, and none overlapped with paths in another shared album. After the user saved two images from album A, its count increased from 7 to 14 unique readable DB paths, all under `cloudsharing/data`, with no path overlap across albums. This confirms the path-match count changed, but it is not an imported-photo count and does not establish the cause or a one-to-one relationship with items saved. The probe tests whether shared DB path references currently point to readable files; it does not query separate regular-library asset records.

For a faster repeat against the Mac mini's locally mounted library, use [`probe_shared_album_paths.py`](../tools/probe_shared_album_paths.py). It opens SQLite read-only, samples up to 20 distinct albums per role code, and checks one referenced file per album without walking the whole package. To inspect every shared-asset reference for one album, pass `--album-title "<album A>"`; this reports database asset/photo/video counts and aggregate path-resolution counts without printing asset filenames. Match the printed album titles to Photos to identify which role code corresponds to albums you created versus albums shared with you.
